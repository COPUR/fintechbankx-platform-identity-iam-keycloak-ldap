# Realm as code: `fintechbankx` (Proposed)

Status: **Proposed**. Owner: Identity Platform Squad (svc-idn-keycloak-ldap).

## Files

| File | Role |
|---|---|
| `realm/service-clients.json` | Client registry: every service client (client id = service id), its service slug, namespace, service account and the audiences it may request; plus the channel clients (web, mobile, TPP template). Edit this first. |
| `scripts/realm/render-realm.mjs` | Renders the realm from the registry and the realm settings in the script. |
| `realm/fintechbankx-realm.json` | Rendered realm representation (Keycloak JSON), applied by keycloak-config-cli. Never edit by hand; CI fails on drift. |
| `realm/admin-permissions.json` | Fine-grained admin permissions (Keycloak 26 FGAP v2): which service client may administer the members of which group, with which scopes and why. |
| `scripts/realm/apply-admin-permissions.mjs` | Applies `realm/admin-permissions.json` through the admin REST API (second step of the import Job; keycloak-config-cli cannot import FGAP v2 permissions). Idempotent: looks up by name and path, creates or updates, never deletes. |
| `scripts/ci/check-realm.mjs` | Contract gate: roles, clients, audiences, FAPI policies, LDAP federation, no credential values, every placeholder supplied by the import Job, no realm-management role on a service client, admin permissions limited to non-staff groups, the TPP client-type rules, Dynamic Client Registration closed. With `--live` (admin API) or `--live-export <file>` (partial export) it checks a running realm instead against the TPP rules and the service-client rules (drift check). |
| `scripts/realm/service-client-rules.mjs` | The service-client rules shared by the static gate and its live drift check: audience mappers and optional `aud-` scopes against the registry, the routes to an `audienceByScope` audience listed under "Audience mappers" below, `fullScopeAllowed=false`, only stock Keycloak 26.7.5 protocol mappers, no standard token exchange, no Authorization Services (no dependencies). |
| `scripts/realm/live-view.mjs` | The view of a running realm (admin API or partial export) and the live errors (TPP and service-client rules), shared by `check-realm.mjs --live`/`--live-export` and `onboard-tpp.mjs --verify-live` (no dependencies, so the import Job can run it). |
| `scripts/realm/tpp-rules.mjs` | The TPP client-type rules shared by `check-realm.mjs` and the onboarding script (no dependencies, so the import Job can run them). |
| `realm/tpp-clients.json` | Open-finance TPP clients to onboard (one spec per TPP: client id, name, redirect URIs, JWKS, payment authorisation). Empty until the first TPP is approved. |
| `scripts/realm/onboard-tpp.mjs` | Creates or repairs TPP clients through the admin API from the realm template (last step of the import Job; also an operator CLI). Idempotent. With `--verify-live` it then checks the running realm against the TPP rules and the service-client rules (registry from `--registry`, default `realm/service-clients.json`; a missing registry stops it before any write). |
| `scripts/realm/tpp-token-drill.mjs` | Drill: obtains a real DPoP-bound TPP access token (PAR, PSU login, consent, code) and checks `fbx_client_type`, `azp`, `scope`, `cnf.jkt`. |

Change flow: edit the registry or the render script, run `node scripts/realm/render-realm.mjs`, run `node scripts/ci/check-realm.mjs` and `npm test`, open a PR. The realm import Job applies the merged file.

## What the realm contains

- **Realm roles** (lower-case, services upper-case them to `ROLE_*`): `customer`, `banker`, `loan_officer`, `admin`, `service`, `auditor`, `compliance_officer`.
- **Groups**: `/staff/fbx-banker`, `/staff/fbx-loan-officer`, `/staff/fbx-admin`, `/staff/fbx-auditor`, `/staff/fbx-compliance-officer` (filled by the LDAP group mapper, each grants the matching role) and `/customers` (role `customer`).
- **16 confidential service clients** (`svc-ln-loan-lifecycle`, `svc-pay-*`, `svc-cus-profile-kyc`, `svc-rsk-decisioning`, `svc-cmp-evidence`, `svc-of-*`, `svc-acc-accounts-ledger`): client credentials only (no browser, implicit, password or device grant), no refresh token, 5-minute access token, `fullScopeAllowed=false` with a scope mapping for `service` only, service account holding realm role `service`. Credential is the placeholder `$(env:FBX_OIDC_SECRET_<CLIENT_ID>)`, resolved at import from Secrets Manager `<env>/<service-slug>/oidc-client`. Every client of the realm file (service, first-party public, TPP template, staff SSO) sets `fullScopeAllowed=false` explicitly; `check-realm.mjs` fails when it is `true` or absent, because Keycloak reads an absent value as `true`.
- **Audience mappers** (platform contract addendum 2026-10-08): every calling client carries one `oidc-audience-mapper` per service id it may call, so `aud` contains the callee's service id. The registry records whether each audience is confirmed by the owning service thread or derived; `check-realm.mjs` fails when an audience has no provenance of the form `confirmed by <source>` or `derived <source>` (a string, the word and a space, then the source), or a provenance names no audience of its client. A callee marked `audienceByScope` in the registry is the exception: its callers (the registry clients, service, channel or staff SSO, whose registry audiences list it) get the optional client scope `aud-<callee>`, which holds that one audience mapper, instead of a mapper, so `aud` carries the callee only in tokens requested with `scope=aud-<callee>`. Today that is the accounts ledger (scope `aud-svc-acc-accounts-ledger`, Platform decision 2026-10-17): the tokens its callers send to customer, consent or their other callees do not carry the ledger audience, and the one-client-per-service rule stays. `check-realm.mjs` fails when such a callee appears as a mapper on any client, when a caller lacks the optional scope or another client has it, when the scope is a client or realm default, or when it carries anything but that one access-token audience mapper. It also fails when any other client scope (`customer-id`, `payments`, the client-type scope, a new scope, a realm default scope) has an audience mapper naming the callee as client or custom audience. On every client and every client scope (realm default scopes included) it refuses any mapper of another type whose `claim.name` starts with the component `aud` when read the way Keycloak reads a claim path (dots split it unless a backslash escapes them, and a backslash stands for the character after it), so `aud`, `aud.`, `\aud`, `a\ud` and `aud.x` are all refused (this realm sets audiences only through `oidc-audience-mapper`). It also refuses any `claim.name` holding `${client_id}` other than the built-in `resource_access.${client_id}.roles`: the client role mapper puts a client id in that place before it reads the path, so with a client named `aud` the name `${client_id}` writes claim `aud`. On every client except the callee's own, and on every client scope, it refuses an `oidc-hardcoded-role-mapper` whose `role` starts with `<callee>.` and an `oidc-role-name-mapper` whose `new.role.name` starts with `<callee>.`. Last, it fails when a client role of the callee is in the role scope of another client or of a client scope. The role mapper routes and the role-scope route work through Keycloak's audience resolve mapper (built-in scope `roles`). That mapper adds the owner of every client role in the token to `aud`, even for a role name that the callee does not define, but it never adds the token's own client, so a callee role on the callee's own client is no route. A client holds a callee role in its role scope when its `fullScopeAllowed` is not `false`, or when an explicit realm-role or client-role scope mapping, or one of its own client roles, is that role or a composite containing it at any depth. A client scope holds one through its own scope mappings. This is Keycloak's `hasScope`. A composite role that is in no role scope is not refused. Keycloak's built-in clients `admin-cli` and `security-admin-console` have `fullScopeAllowed=true`; they are exempt only while their attribute `client.use.lightweight.access.token.enabled` is `"true"`, because their access tokens then carry no `aud`, and only while no `oidc-audience-resolve-mapper` with `lightweight.claim` `"true"` is on the client or in one of its default or optional client scopes, because such a mapper puts `aud` back into lightweight tokens. The exemption assumes that resource servers validate the JWT locally. Token introspection returns the full token, so introspecting a lightweight `admin-cli` token of a user who holds a ledger role returns `aud` with the ledger. Checked since 2026-10-17 (formerly known gaps): (1) script and custom SPI mappers, which can write any claim, `aud` included: on every client and every client scope (Keycloak's built-ins included) `check-realm.mjs`, `--live` and `--live-export` refuse a protocol mapper whose provider id is not one of the 38 stock Keycloak 26.7.5 mappers (`STOCK_PROTOCOL_MAPPERS` in `service-client-rules.mjs`, read from `GET /admin/serverinfo` of a local 26.7.5), so a script mapper (`script-<file>.js`) or a custom SPI mapper fails; `keycloak-cr.test.mjs` keeps the deployment from loading one (base and every overlay: stock image `quay.io/keycloak/keycloak:26.7.5`; no enabled feature but `token-exchange-standard`, so neither `scripts`, `preview`, the legacy `token-exchange`, `token-exchange-delegation` nor `jwt-authorization-grant`; features set in `spec.features` only, never through a `features` option, a `KC_FEATURES*` or `KCKEY_*` env var or `-Dkc.features`; no args, command or envFrom on the Keycloak container; nothing mounted at `/opt/keycloak/providers`; no overlay patch on the image, the features, `spec.env`, the additional options or the pod template). (2) Standard token exchange (Keycloak 26.7.5 feature `token-exchange-standard`, on by default): a client whose attribute `standard.token.exchange.enabled` is `"true"` (any case) can exchange a token that names it in `aud` for a new token of the same user with its own optional scopes; the three modes refuse that attribute on every client, built-ins included, and no client of the realm sets it. (2a) Authorization Services (UMA, Keycloak 26.7.5 feature `authorization`, on by default): on a client with `authorizationServicesEnabled` and a granting policy, any client's token buys an RPT with that client in `aud` (grant type `urn:ietf:params:oauth:grant-type:uma-ticket`, `audience=<client>`), carrying the realm roles of that client's role scope; with it on the ledger client, `svc-cus-profile-kyc` got an RPT with `aud=svc-acc-accounts-ledger` and realm role `service`. The three modes and the import Job refuse `authorizationServicesEnabled` `true` and any `authorizationSettings` on every client, built-ins included, except Keycloak's FGAP v2 client `admin-permissions` (the resource server of the admin permissions); no client of the realm file uses them. (4) The realm import Job applies the service-client rules to the running realm after every sync: its last step, `onboard-tpp.mjs --verify-live --registry /opt/fbx/registry/service-clients.json`, runs them next to the TPP rules on the view of `scripts/realm/live-view.mjs` (the one `check-realm.mjs --live` reads) and fails the Job on any error; `check-realm.test.mjs` runs that command as the Job manifest gives it against an admin API that answers like Keycloak, and fails when a module a Job script imports is missing from the ConfigMap mounted next to it. It matters only for a resource server that introspects tokens.   The accounts ledger audience reaches its four `SERVICE_CALLERS` and the staff web client only, through that optional scope. A caller requests `scope=aud-svc-acc-accounts-ledger` on the client-credentials grant for its ledger calls only (in Spring, a second client registration with the same client id and that scope); a token requested without the scope has no ledger audience and the ledger refuses it, and any other client that asks for the scope gets `invalid_scope`. Staff web carries it since the user decision of 2026-10-17 (option "Staff only"), for the ledger's staff endpoints: `GET /api/v1/accounts/{accountId}`, account open, freeze, unfreeze and close for `banker` and `admin`, `GET /api/v1/journal-entries/{journalEntryId}` for `banker` and `admin`, and `POST /api/v1/journal-entries` for `admin` (ledger `@PreAuthorize`). Staff web is a public PKCE client with no client-credentials grant, so the staff SPA puts `aud-svc-acc-accounts-ledger` in the `scope` parameter of its authorization request; that session's access tokens then carry the ledger audience next to staff web's other audiences. Staff web does not restrict who signs in: any realm user, customers included, can sign in to `fintechbankx-staff-web` with that scope and get a token with the ledger audience, without realm roles and without `customer_id` (local evidence below), which the ledger refuses today. What keeps the ledger staff-only is staff web's role scope (staff roles only) and the ledger's `@PreAuthorize`, not who can obtain the audience; restricting staff web sign-in to staff users (a client authentication-flow override with Condition - user role and Deny access) is not done. A refresh can narrow the scopes but not add one: Keycloak leaves an added scope out of the refreshed token, so a session started without the scope needs a new authorization request. The web and mobile clients still do not carry it, so customer tokens from them are refused by the ledger (`GET /api/v1/accounts/{accountId}` for `customer` own accounts); adding it there is a separate decision (Proposed).

- **Open-finance TPPs (FAPI 2.0)**: TPP access tokens are **DPoP-bound only** (RFC 9449). Client policy `fbx-open-finance-tpp-fapi2-dpop` applies Keycloak's built-in `fapi-2-dpop-security-profile` plus `fbx-open-finance-tpp-client-auth` (client authentication `private_key_jwt` only) to every client tagged `fbx.client-type=open-finance-tpp`; its only condition is that attribute. Together they enforce PAR, PKCE, DPoP, `private_key_jwt` and PS256. The attribute `fbx.tpp.token-binding=dpop` is informational for Keycloak (no policy reads it); `check-realm.mjs` requires it on every TPP client and rejects `mtls` on any client. Dynamic Client Registration is closed (see below); policy `fbx-open-finance-tpp-dynamic-registration` still applies the same two profiles to any registration request, as defence in depth, because attribute conditions only match once a client exists. mTLS certificate-bound tokens (RFC 8705) and `tls_client_auth` are **not** supported: TLS ends at the Istio ingress gateway (mode SIMPLE, no client certificate requested) and Keycloak runs behind plain HTTP, so Keycloak never sees a TPP certificate (security review 2026-10-08 removed the former `fbx-open-finance-tpp-fapi2-mtls` policy). `check-realm.mjs` rejects `fbx.tpp.token-binding=mtls`, `tls.client.certificate.bound.access.tokens`, the `fapi-2-security-profile` and `client-x509` anywhere in the realm. `of-tpp-conformance-template` is a **disabled** reference client and the template every TPP client is built from; real TPP clients are onboarded by the identity platform (below) and never appear in the realm file. PAR request URIs live 60 s.
- **TPP scopes (request-to-pay PR #14, Proposed)**: client scope `payments` (`include.in.token.scope=true`, no claims) is an **optional** scope of TPP clients: the TPP requests `scope=payments` at PAR or token time and the payment services (request to pay, VRP, file payments) require it next to `aud`. Client scope `fbx-client-type-open-finance-tpp` is a **default** scope of TPP clients and adds the access-token claim `fbx_client_type=open-finance-tpp`; Keycloak 26 has no mapper that reads a client attribute, so the value is a hardcoded claim and `check-realm.mjs` fails when it differs from the carrying client's `fbx.client-type`, when any non-TPP client carries either scope, or when either becomes a realm default (a client created without explicit scopes would inherit it). The client-type claim is mandatory on every TPP client (services fail closed when it is absent): `check-realm.mjs` fails for any client tagged `fbx.client-type=open-finance-tpp` without `fbx-client-type-open-finance-tpp` (by name) as a **default** scope, with `payments` as a default scope, or without `fbx.tpp.token-binding=dpop`, and for any client that emits `fbx_client_type` through its own protocol mapper. In the realm file that covers only the template; runtime TPPs are covered below.
- **Runtime TPP onboarding (Proposed, owned by the identity platform)**: identity owns the creation of every open-finance TPP client; consent-authorization (or the TPP onboarding desk) is the caller and asks for a TPP by pull request adding one spec to `realm/tpp-clients.json`. No open-finance repository creates TPP clients itself (no Dynamic Client Registration or admin API calls). The last step of the realm import Job (`tpp-onboarding`, bootstrap admin client, same credential as the earlier steps) runs `scripts/realm/onboard-tpp.mjs --tpps realm/tpp-clients.json --verify-live` on every sync. For each TPP the script builds the client from `of-tpp-conformance-template`, so it carries:
  1. attributes `fbx.client-type=open-finance-tpp` (the FAPI 2.0 DPoP policy above applies on this attribute alone) and `fbx.tpp.token-binding=dpop`;
  2. client scope `fbx-client-type-open-finance-tpp` as a **default** client scope;
  3. client scope `payments` as an **optional** client scope only when the spec says `paymentServices.authorised: true` with an authorisation reference (stored as `fbx.tpp.payment-services-reference`); otherwise no `payments`.

  A spec names the TPP only (`clientId` `of-tpp-<kebab>`, `name`, https `redirectUris`, `jwksUri` or a public `jwks`, `paymentServices`, `status` `active` or `suspended`, default `active`); any other field, any other `status` value, a private JWK member, an http or wildcard redirect URI is refused. The script refuses before any write a client that would break the rules (`scripts/realm/tpp-rules.mjs`), refuses to retype an existing client of another `fbx.client-type`, and is idempotent (update in place, exact default and optional scope lists, nothing else deleted). A new client is created disabled, updated once so Keycloak's open-finance-tpp client policies check it, given its scopes, verified, and only then enabled (a spec listed `suspended` is created and left disabled); on any failure it is deleted again. On update the enabled flag follows `status`, never the template: `suspended` disables the client (see "Suspending and off-boarding a TPP" below); `active` keeps the flag Keycloak holds, so a client an operator disabled stays disabled and the run logs `listed active but disabled in Keycloak; leaving disabled — set status in Git`. Only the create path enables a client. `--verify-live` then fails the Job when any client of the running realm tagged `open-finance-tpp` breaks the rules, or when a non-TPP client carries a TPP scope or emits `fbx_client_type`; with the complete list (`--tpps`, as in the Job) it also fails for an **enabled** `open-finance-tpp` client that `realm/tpp-clients.json` does not list and for a client listed `suspended` that is enabled, and warns for a client listed `active` that is disabled.

  **Credential.** The script needs `manage-clients`. It runs with the import Job's bootstrap admin client, which already holds it, instead of a new standing client: no service client gets a `realm-management` role (`check-realm.mjs` keeps `ADMIN_ROLES_ALLOWED` empty, no exception added), and TPPs are only created from reviewed Git changes. An operator may run the same CLI with that credential for break-glass (`--tpp <spec.json>`, `--dry-run` prints the client without calling Keycloak). A dedicated onboarding client with an FGAP v2 Clients permission was not chosen: a permission can only name existing clients, so creating new ones needs a Clients `manage` permission over all clients (which would also cover the service clients) or a `realm-management` role such as `create-client` (whether FGAP v2 needs both was not verified).

  **What enforces the guarantee, per creation path** (checked locally against Keycloak 26.7.5, see "Local evidence (2026-10-10)"):

  | Path | Enforcement |
  |---|---|

Status: implemented here and drilled locally only; not deployed.
- **Service client baseline policy** (`fbx-service-client-baseline`): client-secret or client-jwt authentication (no `client-x509`; service-to-service mTLS is the mesh's job, not Keycloak's); implicit and password grants rejected; full scope disabled.
- **Tokens and sessions**: access token 300 s; SSO idle 30 min, max 10 h; refresh tokens revoked on use (`revokeRefreshToken`, reuse 0); authorization code 60 s; offline sessions (mobile only) 14 days idle, 30 days max. Realm signs with RS256 (the Spring resource servers accept RS256 by default); FAPI clients are moved to PS256 by the FAPI profile.
- **Brute-force protection**: after 5 failures the account is locked temporarily, waits growing by 60 s up to 15 min. No permanent lockout, so an attacker cannot disable staff accounts; lockouts appear in the login events.

- **Events**: login events (90 days) and admin events with representation details (90 days), plus the `jboss-logging` listener so both reach the log pipeline. The Keycloak CR sets `spi-events-listener--jboss-logging--include-representation=true`, so admin event log lines also carry the representation (the observability alert `KeycloakServiceAccountAdminEventOutOfScope` needs it to see a user disable or a credential change). Those representations can carry personal data (username, email, names, `customer_id`); they are subject to the collector privacy processors and the Loki retention and access rules.
- **User federation**: LDAP provider `fbx-directory`, `READ_ONLY`, import on, StartTLS or LDAPS through the Keycloak truststore, daily full and 15-minute changed-user sync; connection URL, bind DN, bind credential and the directory schema are placeholders (see `DIRECTORY_FEDERATION.md`).

Deviation from `keycloak-aaa-blueprint.md` (enterprise-architecture repo): the blueprint proposes three realms (`open-finance-prod`, `-internal`, `-sandbox`); the platform contract fixes one realm `fintechbankx` per environment. ## Customer user administration (fine-grained admin permissions)

The customer service (`svc-cus-profile-kyc`) links an identity user to a customer profile: `PUT /api/v1/customers/{id}/identity-link` (staff step) reads the user and sets the attribute `customer_id` with `GET` and `PUT /admin/realms/fintechbankx/users/{id}`. It does **not** hold `realm-management` `manage-users` (that would let it edit every user, staff included, and grant itself realm roles). Instead (security review 2026-10-08, option A):

- The realm sets `adminPermissionsEnabled: true` (FGAP v2) and has no `defaultGroups` (a default group would also be joined by every new service account).
- `realm/admin-permissions.json` defines client policy `fbx-customer-service-client` (the client `svc-cus-profile-kyc`, positive) and scope permission `fbx-customers-customer-service` (resource type Groups, resource `/customers`, scopes `view-members` and `manage-members`, decision strategy UNANIMOUS).
- `check-realm.mjs` rejects any `realm-management` role on a service client (service account, scope mapping or registry `adminRoles`) and any admin permission that is not group-scoped, targets `/staff`, uses another scope, or names a client that is not a registered service client.

**Customer users must be created in group `/customers`** (customer onboarding or whoever creates the Keycloak user). A user outside `/customers` is invisible to the customer service: `GET` and `PUT` answer 403.

Verified locally against Keycloak 26.7.5 (realm imported with the pinned keycloak-config-cli 6.5.1 jar, then the script; token of `svc-cus-profile-kyc` by client credentials):

| Call by the customer service | Customer user (in `/customers`) | Staff user |
|---|---|---|
| `GET /users/{id}`, `PUT /users/{id}` (set `customer_id`) | 200, 204 | 403, 403 |
| add realm role, move into `/staff`, remove from `/customers` | 403 | - |
| search, count, create users; list clients, roles, groups; impersonate | 403 | - |
| reset password, read credentials, log out, change email, disable, delete | **allowed** | 403 |

**Residual risk:** `manage-members` is all or nothing for a member, so the customer service can still reset passwords, send required actions, log out, change the email of, disable and delete *customer* users. It cannot touch staff, roles, groups or clients. Admin events (enabled, with representation) record every such call, and the observability alert `KeycloakServiceAccountAdminEventOutOfScope` (observability repository, Loki rule `identity-admin-events`) fires on every one of them except a `PUT /users/{id}` whose representation carries only `username`, `email`, `firstName`, `lastName`, `emailVerified` and `attributes` (the root fields the identity-link PUT writes back). That exception is wider than the owner decision below: see the two paragraphs that follow.

**Owner decision (e-mail and name changes only):** accepted for now by the project owner (decision card, 2026-10-10). On 2026-10-10 at 12:00Z the project owner answered the Platform thread's decision card "Decide how to handle the customer service's power to change customer e-mails in Keycloak" with the option "Accept for now" (the other options were an identity-owned link service and no self-service reset); the CRC thread records the e-mail and name residual-risk entry on that answer. Scope: it accepts, for now, that the customer service credential (`svc-cus-profile-kyc`) can change a customer's e-mail, and the name fields (`firstName`, `lastName`) that its identity-link PUT (`linkCustomer`) carries, without an alert. It does **not** accept credential resets, disable, delete, logout, required actions, role or group changes, or anything outside `/customers`: those still alert. This is not a security-team sign-off: the separate decision card of 2026-10-08 ("Keycloak permission"), which asks for a human sign-off on the remaining `manage-members` residual risk, stays open. Moving this permission to an identity-owned identity-link service that only sets `customer_id` (the customer service would call it instead of the admin API) stays the recommended follow-up; it is not done.

**Not covered by the owner decision (open):** the alert's allow-list (the `representation` branch of `identity-admin-events`, mirrored by `classify` in the observability repository's `keycloak_events_check.py`) also stays silent when the customer service changes `username`, sets `emailVerified` to `true` or `false`, or writes `attributes`. In particular a PUT that sets a new e-mail together with `emailVerified: true` skips the realm's e-mail verification (`verifyEmail: true`), and with `resetPasswordAllowed: true` a password-reset e-mail then goes to that address; this happens without an alert. The owner's "Accept for now" covers e-mail and name changes only, so these changes are **not** accepted: they are part of the remaining `manage-members` residual risk, and the decision card of 2026-10-08 ("Keycloak permission") stays open for them. The realm's user profile lets admins edit `username` and declares `customer_id` as the only attribute beyond the root fields (no unmanaged-attribute policy, so Keycloak should drop other attribute keys); whether Keycloak 26.7.5 applies a `username` change from the admin API while `editUsernameAllowed` is `false`, and that other attribute keys are dropped, was not checked against a running Keycloak. The allow-list cannot drop these keys today because the customer adapter writes `username`, `email`, `firstName`, `lastName` and `emailVerified` back with every identity link (an admin event carries only the new representation, not the old value); closing the gap needs the identity-owned identity-link service above or an adapter that no longer sends them. Neither is done.

The script and config-cli are independent: a re-run of the import keeps the permissions (checked locally), and a permission removed from `admin-permissions.json` is **not** deleted from Keycloak (the script never deletes; remove it in the admin console under Permissions).

## Applying the realm

`deploy/kustomize/base/realm-import/job.yaml` runs keycloak-config-cli 6.5.1 (image pinned by digest) as an initContainer with `IMPORT_VARSUBSTITUTION_ENABLED=true`, then `apply-admin-permissions.mjs` (initContainer) and `onboard-tpp.mjs --verify-live --registry` (container: TPP onboarding, then the TPP and service-client rules on the running realm), both in `node:22.22.0-alpine3.22` (pinned by digest) and receiving only the bootstrap admin client credential. Non-secret inputs come from ConfigMap `keycloak-realm-import-env` (overlay-specific), secret inputs from ExternalSecret `keycloak-realm-import` (admin client, LDAP bind, 17 client credentials: the 16 service clients and the Grafana SSO client). keycloak-config-cli keeps remote state, so a client removed from Git is removed from Keycloak, while clients created outside the realm file (the onboarded TPPs) are left alone. The script never deletes a TPP client.

**Suspending and off-boarding a TPP (Proposed).** Git is the record of a TPP's status; the admin console is not.

1. **Suspend** by pull request setting `"status": "suspended"` on the TPP's spec in `realm/tpp-clients.json`. On the next sync the script disables the client, sets its `notBefore` to the time of that sync (Keycloak then rejects refresh and offline tokens issued before it, also if the client is re-enabled later), and for every user listed by `GET /clients/{id}/user-sessions` and `/offline-sessions` calls `DELETE /users/{userId}/consents/{clientId}`, which revokes that user's consent and offline token for this client and logs the user out of this client only (other sessions of the PSU are kept; a 404, a session without consent or offline token, is tolerated). Access tokens already issued stay valid until they expire (300 s) at resource servers that validate them locally. `POST /clients/{id}/push-revocation` is not used: it only pushes `notBefore` to the client's admin URL, which TPP clients do not have. Evidence level: the endpoints, that an admin client update applies `enabled` and `notBefore`, that the token endpoint checks whether the client is enabled, and that consent revocation also revokes the offline token and logs the user out of the client (only when a consent existed; TPP clients require consent) were read from the Keycloak 26.7.5 server classes; the `notBefore` check at refresh is Keycloak's documented revocation behaviour and was not traced. Nothing here was exercised against a running Keycloak (unit-tested against a fake admin API only). To resume, set `"status": "active"` and re-enable the client in the console once the reason is cleared: the script does not re-enable an existing client. `notBefore` is set when the sync disables an enabled client, and also when the client is already disabled (an operator's console disable, step 3) and its stored `notBefore` is still 0 or missing; a re-run while suspended does not move it. A client that was suspended before, resumed and then disabled in the console keeps its earlier `notBefore`: that sync revokes the sessions but does not move `notBefore`.
2. **Off-board** with a second pull request removing the spec once the client is disabled (the Job's listing check fails if an enabled TPP client is unlisted, so removing an active spec without step 1 is caught). The disabled client is then left alone; delete it in the admin console when it is no longer needed as evidence (the script never deletes a TPP client).
3. **Console disable** (break-glass, for example during an incident) is honoured: the next sync leaves the client disabled but logs `listed active but disabled in Keycloak; leaving disabled — set status in Git` and the `--verify-live` step repeats it as a warning on every sync until Git says `suspended`. The console disable alone sets no `notBefore` and revokes no session; follow it with step 1, whose sync then sets `notBefore` (when it is still 0 or missing) and revokes the sessions although the client is already disabled.

**Removals on an existing realm.** keycloak-config-cli 6.5.1 with its defaults does not remove everything Git removes (checked locally by importing the previous realm and then this one):

- realm roles dropped from a client's scope mapping stay (`import.managed.scope-mapping=no-delete`; role removal is tied to `import.managed.client-scope=full`, which would also delete Keycloak's built-in client scopes such as `service_account` and strip `offline_access`, so it is not used). The Job's second step therefore removes every realm role the realm file no longer lists for a client (`reconcileScopeMappings` in `apply-admin-permissions.mjs`).
- a user's client roles are only reconciled for clients named in that user's `clientRoles`, and client scope mappings only when `clientScopeMappings` is present. The render therefore writes `clientRoles: {"realm-management": []}` on every service account and `clientScopeMappings: {}`; `check-realm.mjs` requires both.

With both in place, an upgrade from the previous realm removed `manage-users` from `svc-cus-profile-kyc` (service account and scope mapping) and the staff roles from `fintechbankx-web` and `fintechbankx-mobile`, and left the built-in client scopes intact.

KeycloakRealmImport (operator CR) is not used: it only creates a missing realm and never updates an existing one.

**Rollout order for the ledger audience scope (Platform decision 2026-10-17).** In each environment:
1. Import the realm that carries `aud-svc-acc-accounts-ledger`.
2. Deploy the four callers (`payment-initiation-settlement`, `payment-recurring-mandates`, `payment-bulk-orchestration`, `loan-lifecycle`) together, in the same change window, with their ledger client registration requesting that scope.
3. Deploy the staff SPA with that scope in its authorization request. Before step 1 staff web does not have the scope, and Keycloak answers that request with `error=invalid_scope`.

Between the two steps, ledger calls fail closed. A caller still on its old version gets a token without the ledger audience, and the ledger answers 401. A caller deployed before the import asks for a scope the realm does not have, and the token endpoint answers `invalid_scope`.

There is no transitional realm carrying both the old always-on mapper and the new scope. It would put the ledger audience back into every token these callers send for the whole transition, and `check-realm.mjs` refuses that configuration.

No environment runs the ledger yet, so the first rollout has no gap.

**Rollback.** Rolling the callers back to a version that does not request the scope also means importing the previous realm, the one with the always-on mapper.
