# Realm as code: `fintechbankx` (Proposed)

Status: **Proposed**. Owner: Identity Platform Squad (svc-idn-keycloak-ldap).

## Files

| File | Role |
|---|---|
| `realm/service-clients.json` | Client registry: every service client (client id = service id), its service slug, namespace, service account and the audiences it may request; plus the channel clients (web, mobile, TPP template). Edit this first. |
| `scripts/realm/render-realm.mjs` | Renders the realm from the registry and the realm settings in the script. |
| `realm/fintechbankx-realm.json` | Rendered realm representation (Keycloak JSON), applied by keycloak-config-cli. Never edit by hand; CI fails on drift. |
| `realm/admin-permissions.json` | Fine-grained admin permissions (Keycloak 26 FGAP v2): which service client may administer the members of which group, with which scopes and why. |
| `scripts/realm/apply-admin-permissions.mjs` | Applies `realm/admin-permissions.json` through the admin REST API (second step of the import Job; keycloak-config-cli cannot import FGAP v2 permissions). Idempotent: looks up by name and path, creates or updates, never deletes. |
| `scripts/ci/check-realm.mjs` | Contract gate: roles, clients, audiences, FAPI policies, LDAP federation, no credential values, every placeholder supplied by the import Job, no realm-management role on a service client, admin permissions limited to non-staff groups, the TPP client-type rules, Dynamic Client Registration closed. With `--live` (admin API) or `--live-export <file>` (partial export) it checks a running realm instead against the TPP rules and the service-client rules (drift check). |
| `scripts/realm/service-client-rules.mjs` | The service-client rules shared by the static gate and its live drift check: audience mappers and optional `aud-` scopes against the registry, the routes to an `audienceByScope` audience listed under "Audience mappers" below, `fullScopeAllowed=false`, only stock Keycloak 26.7.5 protocol mappers, no standard token exchange, no Authorization Services (no dependencies). |
| `scripts/realm/live-view.mjs` | The view of a running realm (admin API or partial export) and the live errors (TPP and service-client rules), shared by `check-realm.mjs --live`/`--live-export` and `onboard-tpp.mjs --verify-live` (no dependencies, so the import Job can run it). |
| `scripts/realm/tpp-rules.mjs` | The TPP client-type rules shared by `check-realm.mjs` and the onboarding script (no dependencies, so the import Job can run them). |
| `realm/tpp-clients.json` | Open-finance TPP clients to onboard (one spec per TPP: client id, name, redirect URIs, JWKS, payment authorisation). Empty until the first TPP is approved. |
| `scripts/realm/onboard-tpp.mjs` | Creates or repairs TPP clients through the admin API from the realm template (last step of the import Job; also an operator CLI). Idempotent. With `--verify-live` it then checks the running realm against the TPP rules and the service-client rules (registry from `--registry`, default `realm/service-clients.json`; a missing registry stops it before any write). |
| `scripts/realm/tpp-token-drill.mjs` | Drill: obtains a real DPoP-bound TPP access token (PAR, PSU login, consent, code) and checks `fbx_client_type`, `azp`, `scope`, `cnf.jkt`. |

Change flow: edit the registry or the render script, run `node scripts/realm/render-realm.mjs`, run `node scripts/ci/check-realm.mjs` and `npm test`, open a PR. The realm import Job applies the merged file.

## What the realm contains

- **Realm roles** (lower-case, services upper-case them to `ROLE_*`): `customer`, `banker`, `loan_officer`, `admin`, `service`, `auditor`, `compliance_officer`, and the four separation-of-duties markers `sod_cmp_maker`, `sod_cmp_checker`, `sod_pay_maker`, `sod_pay_checker` (11 in all; see "Separation of duties for bpo staff queues").
- **Groups**: `/staff/fbx-banker`, `/staff/fbx-loan-officer`, `/staff/fbx-admin`, `/staff/fbx-auditor`, `/staff/fbx-compliance-officer` (filled by the LDAP group mapper, each grants the matching role), the ten bpo queue groups `/staff/fbx-cmp-ae-onboarding-l1`, `/staff/fbx-cmp-tr-onboarding-l1`, `/staff/fbx-cmp-review-l1`, `/staff/fbx-cmp-ae-mlro`, `/staff/fbx-cmp-tr-compliance-officer`, `/staff/fbx-cmp-review-l2`, `/staff/fbx-pay-tr-fast-ops`, `/staff/fbx-pay-ops-l1`, `/staff/fbx-pay-tr-fast-supervisor`, `/staff/fbx-pay-ops-l2` (each grants one marker role; 15 staff groups in all) and `/customers` (role `customer`).
- **16 confidential service clients** (`svc-ln-loan-lifecycle`, `svc-pay-*`, `svc-cus-profile-kyc`, `svc-rsk-decisioning`, `svc-cmp-evidence`, `svc-of-*`, `svc-acc-accounts-ledger`): client credentials only (no browser, implicit, password or device grant), no refresh token, 5-minute access token, `fullScopeAllowed=false` with a scope mapping for `service` only, service account holding realm role `service`. Credential is the placeholder `$(env:FBX_OIDC_SECRET_<CLIENT_ID>)`, resolved at import from Secrets Manager `<env>/<service-slug>/oidc-client`. Every client of the realm file (service, first-party public, TPP template, staff SSO) sets `fullScopeAllowed=false` explicitly; `check-realm.mjs` fails when it is `true` or absent, because Keycloak reads an absent value as `true`.
- **Audience mappers** (platform contract addendum 2026-10-08): every calling client carries one `oidc-audience-mapper` per service id it may call, so `aud` contains the callee's service id. The registry records whether each audience is confirmed by the owning service thread or derived; `check-realm.mjs` fails when an audience has no provenance of the form `confirmed by <source>` or `derived <source>` (a string, the word and a space, then the source), or a provenance names no audience of its client. A callee marked `audienceByScope` in the registry is the exception: its callers (the registry clients, service, channel or staff SSO, whose registry audiences list it) get the optional client scope `aud-<callee>`, which holds that one audience mapper, instead of a mapper, so `aud` carries the callee only in tokens requested with `scope=aud-<callee>`. Today that is the accounts ledger (scope `aud-svc-acc-accounts-ledger`, Platform decision 2026-10-17): the tokens its callers send to customer, consent or their other callees do not carry the ledger audience, and the one-client-per-service rule stays. `check-realm.mjs` fails when such a callee appears as a mapper on any client, when a caller lacks the optional scope or another client has it, when the scope is a client or realm default, or when it carries anything but that one access-token audience mapper. It also fails when any other client scope (`customer-id`, `payments`, the client-type scope, a new scope, a realm default scope) has an audience mapper naming the callee as client or custom audience. On every client and every client scope (realm default scopes included) it refuses any mapper of another type whose `claim.name` starts with the component `aud` when read the way Keycloak reads a claim path (dots split it unless a backslash escapes them, and a backslash stands for the character after it), so `aud`, `aud.`, `\aud`, `a\ud` and `aud.x` are all refused (this realm sets audiences only through `oidc-audience-mapper`). It also refuses any `claim.name` holding `${client_id}` other than the built-in `resource_access.${client_id}.roles`: the client role mapper puts a client id in that place before it reads the path, so with a client named `aud` the name `${client_id}` writes claim `aud`. On every client except the callee's own, and on every client scope, it refuses an `oidc-hardcoded-role-mapper` whose `role` starts with `<callee>.` and an `oidc-role-name-mapper` whose `new.role.name` starts with `<callee>.`. Last, it fails when a client role of the callee is in the role scope of another client or of a client scope. The role mapper routes and the role-scope route work through Keycloak's audience resolve mapper (built-in scope `roles`). That mapper adds the owner of every client role in the token to `aud`, even for a role name that the callee does not define, but it never adds the token's own client, so a callee role on the callee's own client is no route. A client holds a callee role in its role scope when its `fullScopeAllowed` is not `false`, or when an explicit realm-role or client-role scope mapping, or one of its own client roles, is that role or a composite containing it at any depth. A client scope holds one through its own scope mappings. This is Keycloak's `hasScope`. A composite role that is in no role scope is not refused. Keycloak's built-in clients `admin-cli` and `security-admin-console` have `fullScopeAllowed=true`; they are exempt only while their attribute `client.use.lightweight.access.token.enabled` is `"true"`, because their access tokens then carry no `aud`, and only while no `oidc-audience-resolve-mapper` with `lightweight.claim` `"true"` is on the client or in one of its default or optional client scopes, because such a mapper puts `aud` back into lightweight tokens. The exemption assumes that resource servers validate the JWT locally. Token introspection returns the full token, so introspecting a lightweight `admin-cli` token of a user who holds a ledger role returns `aud` with the ledger. The three modes and the import Job refuse any `authorizationServicesEnabled` other than absent, `false` or `"false"` in any case (Keycloak and keycloak-config-cli read `"true"`, `"True"`, `"TRUE"` and space-padded forms as true) and any `authorizationSettings` on every client, built-ins included, except Keycloak's FGAP v2 client `admin-permissions` (the resource server of the admin permissions); no client of the realm file uses them. (4) The realm import Job applies the service-client rules to the running realm after every sync: its last step, `onboard-tpp.mjs --verify-live --registry /opt/fbx/registry/service-clients.json`, runs them next to the TPP rules on the view of `scripts/realm/live-view.mjs` (the one `check-realm.mjs --live` reads) and fails the Job on any error; `check-realm.test.mjs` runs that command as the Job manifest gives it against an admin API that answers like Keycloak, and fails when a module a Job script imports is missing from the ConfigMap mounted next to it. (5) Who signs in to staff web (DevSecOps review 2026-10-17): `fintechbankx-staff-web` binds its browser flow (`authenticationFlowBindingOverrides`, key `browser`) to `fbx-staff-browser`, which signs the user in as Keycloak's built-in browser flow does (SSO cookie, else username and password, then OTP when the user has one configured; no Kerberos and no identity provider) and then denies any user who holds none of `banker`, `loan_officer`, `admin`, `auditor` and `compliance_officer` (one negated `conditional-user-role` per role in one conditional subflow, whose conditions Keycloak ANDs, then `deny-access-authenticator`). Only users who hold a staff role at sign-in (from the `/staff/fbx-*` groups) get a staff web token and its audiences, the ledger's among them; an SSO session started at `fintechbankx-web` is refused at staff web too: the plain cookie visit gets the 401 "Access denied" page, and with `prompt=none` Keycloak answers with a redirect carrying `error=login_required`. The check runs at sign-in only: a refresh of an existing staff web session does not check roles again (Keycloak 26.7.5's refresh grant runs no flow), and a staff web session lasts until staff web's `client.session.max.lifespan` and `client.session.idle.timeout` end it (8 hours at most, 15 minutes idle). A removal from a staff group in the directory also reaches Keycloak only later: the LDAP provider (`cachePolicy` `DEFAULT`, `changedSyncPeriod` 900 s) keeps the user's cached group membership until the next changed-users sync or another eviction, and in that window new sign-ins still pass the staff check and get staff web tokens, the ledger audience included, each session refreshable for up to 8 hours. Without a step in Keycloak the exposure is up to about 8 hours plus that window. The changed-users sync evicts only users whose own directory entry changed, which a group change need not do (Active Directory's `memberOf` is a back-link); the window then lasts until the daily full sync (`fullSyncPeriod` 86400 s) or another eviction (read from the Keycloak 26.7.5 classes, not run). An LDAP-only change never calls Keycloak, so the offboarding step, for a leaver or a staff group removed, must log out the user's sessions in Keycloak (`POST /admin/realms/<realm>/users/{id}/logout`) or disable the user. While the old membership is cached a logout alone does not stop a new sign-in with a directory password that still works, so a user who keeps a directory account is disabled in Keycloak until the change has synced. "Forgot password" ends in a sign-in to the client it started from through the realm's reset credentials flow, which no client override reaches (with the built-in flow a customer reset from staff web's login page and got a staff web token with the ledger audience; local evidence below), so the realm's reset flow is `fbx-reset-credentials`: the built-in one plus the same staff check after the e-mail step, before the new password is set, run only for a client that has the marker client scope `fbx-staff-channel` as a default scope (`conditional-client-scope`; staff web carries it, the scope has no mappers and is not in the token's `scope` claim). The page before the e-mail is the same for every username, and staff and customers alike get the e-mail, so the staff check adds nothing observable before the link; Keycloak's built-in e-mail step still answers more slowly when it sends a mail. Self-registration and identity providers would sign users in through flows without the check, and direct grant through the realm's direct grant flow, so the realm allows neither and staff web keeps direct grant off. Keycloak's role and client-scope conditions are false for a name they cannot resolve, whatever `negate` says, so one unknown role would let every user through: `check-realm.mjs`, `--live`, `--live-export` and the import Job refuse a staff channel client (registry `userType` `staff`) whose browser override is not `fbx-staff-browser`, that lacks the marker as a default scope or allows direct grant; a realm reset flow other than `fbx-reset-credentials`; any difference in either flow tree (order, requirements, authenticators, config keys and values, `negate` other than as built; compared as structures, so a config value holding `,` or `=` cannot pass for two keys); two executions with one priority or executions listed out of priority order (keycloak-config-cli creates subflows in list order); a staff config alias that another config shares (`--live` sees only the configs that executions use, see "Live drift check" below); a staff role missing from the realm roles; a staff role in the composites (at any depth, through client roles too) of another realm role or of the default role `default-roles-<realm>`, which every user holds, and, in the realm file, a staff role on a group outside `/staff/fbx-*` or on a realm-file user other than a service account (directly, through composites or through any group, `/staff/fbx-*` included: realm-file users are local, not from the directory) (Keycloak's role condition counts composites, default roles and group roles); in the realm file, the legacy key `defaultRoles` on the realm or a client (with no `defaultRole` in the file Keycloak adds those roles to the default role); a missing marker scope or one with mappers; `registrationAllowed` other than `false`, absent or a string Jackson reads as false (`"false"`, `"False"` or `"FALSE"`, space-padded or not; another spelling fails the import); and any identity provider. Staff roles come from the directory through one LDAP provider, and `check-realm.mjs` holds it to that: one user storage provider, the LDAP provider, whose mappers are the attribute mappers (`user-attribute-ldap-mapper`) and one read-only `group-ldap-mapper` with `groups.path` `/staff`, `groups.ldap.filter` `(cn=fbx-*)`, group names from `cn` and no nested groups, so directory groups land only in `/staff/fbx-*`; it refuses `hardcoded-ldap-role-mapper` (a fixed role for every federated user), `role-ldap-mapper`, `hardcoded-ldap-group-mapper`, a second group mapper and any other mapper. LDAP mapper integrity is a static guarantee only: `--live` and `--live-export` do not read the LDAP provider, so a mapper added through the admin console is not caught between imports. Residual risk (owner decision; Platform proposes accepting it): Keycloak's brute-force detection counts every denial as a failed login. A customer signed in at `fintechbankx-web` whose browser loads staff web's authorization URL, for example from another site (Keycloak's SSO cookies are `SameSite=None`), is denied once per load; two denials within a second lock that customer's new password sign-ins for 60 seconds, repeated ones for up to 15 minutes (realm brute-force settings), while the current SSO session keeps working (local evidence below). Anyone who knows a customer's username could already cause that lockout with wrong passwords; this route needs no username. Staff users in a realm of their own (separate cookies and counters) would remove it. ## Customer user administration (fine-grained admin permissions)

The customer service (`svc-cus-profile-kyc`) links an identity user to a customer profile: `PUT /api/v1/customers/{id}/identity-link` (staff step) reads the user and sets the attribute `customer_id` with `GET` and `PUT /admin/realms/fintechbankx/users/{id}`. It does **not** hold `realm-management` `manage-users` (that would let it edit every user, staff included, and grant itself realm roles). Instead (security review 2026-10-08, option A):

- The realm sets `adminPermissionsEnabled: true` (FGAP v2) and has no `defaultGroups` (a default group would also be joined by every new service account).
- `realm/admin-permissions.json` defines client policy `fbx-customer-service-client` (the client `svc-cus-profile-kyc`, positive) and scope permission `fbx-customers-customer-service` (resource type Groups, resource `/customers`, scopes `view-members` and `manage-members`, decision strategy UNANIMOUS).
- `check-realm.mjs` rejects any `realm-management` role on a service client (service account, scope mapping or registry `adminRoles`) and any admin permission that is not group-scoped, targets `/staff`, uses another scope, or names a client that is not a registered service client.

**Customer users must be created in group `/customers`** (customer onboarding or whoever creates the Keycloak user). A user outside `/customers` is invisible to the customer service: `GET` and `PUT` answer 403.

Verified locally against Keycloak 26.7.5 (realm imported with the pinned keycloak-config-cli 6.5.1 jar, then the script; token of `svc-cus-profile-kyc` by client credentials):

| Call by the customer service | Customer user (in `/customers`) | Staff user |
|---|---|---|
| `GET /users/{id}`, `PUT /users/{id}` (set `customer_id`) | 200, 204 | 403, 403 |
| add realm role, move into `/staff`, remove from `/customers` | 403 | - |
| search, count, create users; list clients, roles, groups; impersonate | 403 | - |
| reset password, read credentials, log out, change email, disable, delete | **allowed** | 403 |

**Residual risk:** `manage-members` is all or nothing for a member, so the customer service can still reset passwords, send required actions, log out, change the email of, disable and delete *customer* users. It cannot touch staff, roles, groups or clients. Admin events (enabled, with representation) record every such call, and the observability alert `KeycloakServiceAccountAdminEventOutOfScope` (observability repository, Loki rule `identity-admin-events`) fires on every one of them except a `PUT /users/{id}` whose representation carries only `username`, `email`, `firstName`, `lastName`, `emailVerified` and `attributes` (the root fields the identity-link PUT writes back). That exception is wider than the owner decision below: see the two paragraphs that follow.

**Owner decision (e-mail and name changes only):** accepted for now by the project owner (decision card, 2026-10-10). On 2026-10-10 at 12:00Z the project owner answered the Platform thread's decision card "Decide how to handle the customer service's power to change customer e-mails in Keycloak" with the option "Accept for now" (the other options were an identity-owned link service and no self-service reset); the CRC thread records the e-mail and name residual-risk entry on that answer. Scope: it accepts, for now, that the customer service credential (`svc-cus-profile-kyc`) can change a customer's e-mail, and the name fields (`firstName`, `lastName`) that its identity-link PUT (`linkCustomer`) carries, without an alert. It does **not** accept credential resets, disable, delete, logout, required actions, role or group changes, or anything outside `/customers`: those still alert. This is not a security-team sign-off: the separate decision card of 2026-10-08 ("Keycloak permission"), which asks for a human sign-off on the remaining `manage-members` residual risk, stays open. Moving this permission to an identity-owned identity-link service that only sets `customer_id` (the customer service would call it instead of the admin API) stays the recommended follow-up; it is not done.

**Not covered by the owner decision (open):** the alert's allow-list (the `representation` branch of `identity-admin-events`, mirrored by `classify` in the observability repository's `keycloak_events_check.py`) also stays silent when the customer service changes `username`, sets `emailVerified` to `true` or `false`, or writes `attributes`. In particular a PUT that sets a new e-mail together with `emailVerified: true` skips the realm's e-mail verification (`verifyEmail: true`), and with `resetPasswordAllowed: true` a password-reset e-mail then goes to that address; this happens without an alert. The owner's "Accept for now" covers e-mail and name changes only, so these changes are **not** accepted: they are part of the remaining `manage-members` residual risk, and the decision card of 2026-10-08 ("Keycloak permission") stays open for them. The realm's user profile lets admins edit `username` and declares `customer_id` as the only attribute beyond the root fields (no unmanaged-attribute policy, so Keycloak should drop other attribute keys); whether Keycloak 26.7.5 applies a `username` change from the admin API while `editUsernameAllowed` is `false`, and that other attribute keys are dropped, was not checked against a running Keycloak. The allow-list cannot drop these keys today because the customer adapter writes `username`, `email`, `firstName`, `lastName` and `emailVerified` back with every identity link (an admin event carries only the new representation, not the old value); closing the gap needs the identity-owned identity-link service above or an adapter that no longer sends them. Neither is done.

**Merge with the residual risk open (Platform recommendation, Proposed, 2026-10-19):** the two pull request review threads on `manage-members` were resolved so that this repository can merge; on 2026-10-19 the project owner asked for the merge to be unblocked. That request is not an explicit acceptance of the residual risk above: the decision card of 2026-10-08 ("Keycloak permission") stays open, and so does the part that the paragraph above leaves open. Platform recommends accepting the residual risk only until go-live. Before any production environment imports this realm, the identity-owned identity-link service (it sets only `customer_id`; the customer service calls it instead of the admin API) must replace the customer service's `manage-members` permission on `/customers`. That replacement is a go-live item, owned by Platform, and is not built. Until then, the alert `KeycloakServiceAccountAdminEventOutOfScope` remains the only control on credential resets, disable, delete and logout of customer users, and `username`, `emailVerified` and `attributes` changes stay silent.

The script and config-cli are independent: a re-run of the import keeps the permissions (checked locally), and a permission removed from `admin-permissions.json` is **not** deleted from Keycloak (the script never deletes; remove it in the admin console under Permissions).

## Separation of duties for bpo staff queues

**Rule (go-live item G-S1).** One person may not work both the maker and the checker side of a bpo staff queue. The decision is recorded in the bpo repository (`docs/identity-requests.md`): identity enforces the rule at sign-in, and refusing the same person on both sides of one task is a separate requirement owned by the bpo service. The bpo side is reported as implemented in bpo PR #4 (branch `claude/project-thread-grzfo1`, commit `f0729d5`: the API refuses a checker claim or decision by the maker task's last assignee); that is not verified from this repository. The pairs are:

- compliance (`<jurisdiction>` is lower-case letters and digits, optionally in hyphen-joined parts): `fbx-cmp-<jurisdiction>-onboarding-l1` or `fbx-cmp-review-l1` (maker) against `fbx-cmp-<jurisdiction>-mlro`, `fbx-cmp-tr-compliance-officer` or `fbx-cmp-review-l2` (checker);
- payments: `fbx-pay-tr-fast-ops` or `fbx-pay-ops-l1` (maker) against `fbx-pay-tr-fast-supervisor` or `fbx-pay-ops-l2` (checker).

**How it is built.** Each queue is a directory group with `cn` `fbx-<queue>`, so the LDAP group mapper lands it at `/staff/fbx-<queue>`. In the realm file each queue group grants one marker realm role: `sod_cmp_maker`, `sod_cmp_checker`, `sod_pay_maker` or `sod_pay_checker` (`SOD_RULES` in `service-client-rules.mjs`). The staff browser flow `fbx-staff-browser` runs one conditional subflow per rule after the staff check (`fbx-staff-browser sod cmp`, `fbx-staff-browser sod pay`): two `conditional-user-role` conditions, maker role and checker role, not negated, which Keycloak ANDs, then `deny-access-authenticator`. A user in both a maker and a checker group of one rule is denied. The reset flow `fbx-reset-credentials` runs the same subflows for staff channel clients (marker scope `fbx-staff-channel`) after the staff check and before the new password. The realm keeps `editUsernameAllowed` `false`, and staff are federated from a read-only LDAP provider, so `preferred_username` does not change through Keycloak.

**Gate.** `check-realm.mjs` and the live modes refuse a missing marker role (an unknown role makes the condition false for every user, so the check would let everyone through) and any difference in the subflows. They also refuse `editUsernameAllowed` other than `false`, absent or a string Jackson reads as false. They also refuse a marker role in the composites of any realm role or of the default role (the default role's would deny every user of the other side). In the realm file they refuse a `/staff/fbx-*` group whose name matches a maker or checker pattern but does not grant its marker, a group that grants both markers of one rule, a `/staff/fbx-cmp-*` or `/staff/fbx-pay-*` group that matches neither side (so a new queue must be added to `SOD_RULES` before it is defined), a marker on any group other than its own queue groups, and a marker held by a realm-file user (directly, through composites or through a group).

**Limits.**

- The check runs at sign-in and at password reset only. A session that started before a person was added to the second group keeps refreshing until it ends (8 hours at most), and LDAP caching can delay a group change, as item (5) under "What the realm contains" describes. Within that window this realm does not stop one person from acting on both sides; that is the residual risk, and closing it is the bpo service's requirement above (not verified from identity).
- A queue group must be defined in the realm file to carry its marker. A directory group `fbx-<queue>` that the realm file does not define reaches Keycloak with no role, so the separation check does not see it. The live modes read no groups, so this is a static guarantee only.
- The check applies only to clients whose browser flow is `fbx-staff-browser`. A bpo staff UI client must use that flow, and its users still need a staff role to pass the staff check.
- `preferred_username` comes from the directory, so a rename in the directory changes it. Audit trails that must survive a rename should also record `sub`.

## Applying the realm

`deploy/kustomize/base/realm-import/job.yaml` runs keycloak-config-cli 6.5.1 (image pinned by digest) as an initContainer with `IMPORT_VARSUBSTITUTION_ENABLED=true`, then `apply-admin-permissions.mjs` (initContainer) and `onboard-tpp.mjs --verify-live --registry` (container: TPP onboarding, then the TPP and service-client rules on the running realm), both in `node:22.22.0-alpine3.22` (pinned by digest) and receiving only the bootstrap admin client credential. Non-secret inputs come from ConfigMap `keycloak-realm-import-env` (overlay-specific), secret inputs from ExternalSecret `keycloak-realm-import` (admin client, LDAP bind, 17 client credentials: the 16 service clients and the Grafana SSO client). keycloak-config-cli keeps remote state, so a client removed from Git is removed from Keycloak, while clients created outside the realm file (the onboarded TPPs) are left alone. The script never deletes a TPP client.

**Suspending and off-boarding a TPP (Proposed).** Git is the record of a TPP's status; the admin console is not.

1. **Suspend** by pull request setting `"status": "suspended"` on the TPP's spec in `realm/tpp-clients.json`. On the next sync the script disables the client, sets its `notBefore` to the time of that sync (Keycloak then rejects refresh and offline tokens issued before it, also if the client is re-enabled later), and for every user listed by `GET /clients/{id}/user-sessions` and `/offline-sessions` calls `DELETE /users/{userId}/consents/{clientId}`, which revokes that user's consent and offline token for this client and logs the user out of this client only (other sessions of the PSU are kept; a 404, a session without consent or offline token, is tolerated). Access tokens already issued stay valid until they expire (300 s) at resource servers that validate them locally. `POST /clients/{id}/push-revocation` is not used: it only pushes `notBefore` to the client's admin URL, which TPP clients do not have. Evidence level: the endpoints, that an admin client update applies `enabled` and `notBefore`, that the token endpoint checks whether the client is enabled, and that consent revocation also revokes the offline token and logs the user out of the client (only when a consent existed; TPP clients require consent) were read from the Keycloak 26.7.5 server classes; the `notBefore` check at refresh is Keycloak's documented revocation behaviour and was not traced. Nothing here was exercised against a running Keycloak (unit-tested against a fake admin API only). To resume, set `"status": "active"` and re-enable the client in the console once the reason is cleared: the script does not re-enable an existing client. `notBefore` is set when the sync disables an enabled client, and also when the client is already disabled (an operator's console disable, step 3) and its stored `notBefore` is still 0 or missing; a re-run while suspended does not move it. A client that was suspended before, resumed and then disabled in the console keeps its earlier `notBefore`: that sync revokes the sessions but does not move `notBefore`.
2. **Off-board** with a second pull request removing the spec once the client is disabled (the Job's listing check fails if an enabled TPP client is unlisted, so removing an active spec without step 1 is caught). The disabled client is then left alone; delete it in the admin console when it is no longer needed as evidence (the script never deletes a TPP client).
3. **Console disable** (break-glass, for example during an incident) is honoured: the next sync leaves the client disabled but logs `listed active but disabled in Keycloak; leaving disabled — set status in Git` and the `--verify-live` step repeats it as a warning on every sync until Git says `suspended`. The console disable alone sets no `notBefore` and revokes no session; follow it with step 1, whose sync then sets `notBefore` (when it is still 0 or missing) and revokes the sessions although the client is already disabled.

**Removals on an existing realm.** keycloak-config-cli 6.5.1 with its defaults does not remove everything Git removes (checked locally by importing the previous realm and then this one):

- realm roles dropped from a client's scope mapping stay (`import.managed.scope-mapping=no-delete`; role removal is tied to `import.managed.client-scope=full`, which would also delete Keycloak's built-in client scopes such as `service_account` and strip `offline_access`, so it is not used). The Job's second step therefore removes every realm role the realm file no longer lists for a client (`reconcileScopeMappings` in `apply-admin-permissions.mjs`).
- a user's client roles are only reconciled for clients named in that user's `clientRoles`, and client scope mappings only when `clientScopeMappings` is present. The render therefore writes `clientRoles: {"realm-management": []}` on every service account and `clientScopeMappings: {}`; `check-realm.mjs` requires both.

With both in place, an upgrade from the previous realm removed `manage-users` from `svc-cus-profile-kyc` (service account and scope mapping) and the staff roles from `fintechbankx-web` and `fintechbankx-mobile`, and left the built-in client scopes intact.

KeycloakRealmImport (operator CR) is not used: it only creates a missing realm and never updates an existing one.

**Rollout order for the ledger audience scope (Platform decision 2026-10-17).** In each environment:
1. Import the realm that carries `aud-svc-acc-accounts-ledger`.
2. Deploy the four callers (`payment-initiation-settlement`, `payment-recurring-mandates`, `payment-bulk-orchestration`, `loan-lifecycle`) together, in the same change window, with their ledger client registration requesting that scope.
3. Deploy the staff SPA with that scope in its authorization request. Before step 1 staff web does not have the scope, and Keycloak answers that request with `error=invalid_scope`.

Between the two steps, ledger calls fail closed. A caller still on its old version gets a token without the ledger audience, and the ledger answers 401. A caller deployed before the import asks for a scope the realm does not have, and the token endpoint answers `invalid_scope`.

There is no transitional realm carrying both the old always-on mapper and the new scope. It would put the ledger audience back into every token these callers send for the whole transition, and `check-realm.mjs` refuses that configuration.

No environment runs the ledger yet, so the first rollout has no gap.

**Rollback.** Rolling the callers back to a version that does not request the scope also means importing the previous realm, the one with the always-on mapper.
